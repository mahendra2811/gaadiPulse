# Plan: country, time zone and currency onboarding

Status: **Planning only — not implemented or deployed.** This plan collects the changes for a later coordinated implementation. It does not authorize a database reset, currency conversion, or reinterpretation of existing amounts.

## Goal and confirmed decisions

- During first-time account setup, ask for country, time zone and preferred currency, along with the existing name and authenticated email. India can suggest INR and `Asia/Kolkata`; the United States can suggest USD and offer its applicable time zones. Users can override suggestions.
- New vehicles inherit the account's choices, with an editable vehicle time zone and default currency. A vehicle can use a different currency from its owner's account default. Existing vehicles and records must not be silently changed when the account preference changes.
- Currency selection applies as the default for future entries. **Each existing record retains its original currency**, as the user already confirmed. Changing a vehicle's default affects future records only; it is not a conversion.
- Country is a user-selected preference, not proof of residence, nationality, identity or location. Do not request GPS, use IP-based geolocation, or infer currency solely from a country without allowing correction.
- Ask separately about a distinct username only if the product needs one. The current profile stores a display name and verified authentication email; it has no username. Define uniqueness, visibility and edit rules before adding a username rather than treating email or display name as a globally unique handle.

## Current state in this repository

1. `src/features/auth/profile.ts` persists display name, theme and an IANA time zone; `src/features/auth/settings.tsx` uses the profile form for first setup. Account time-zone selection and applying it to the new-vehicle form have been partially implemented in the workspace but have not been verified with live sign-up. There is no country, currency, username or explicit onboarding-completion field.
2. `src/features/garage/VehicleForm.tsx` and `src/features/garage/schema.ts` use a per-vehicle time zone. `supabase/migrations/202610210004_hardening.sql` defines `save_vehicle`; `list_my_vehicles` is defined in the foundation migration. Neither currently includes country or currency.
3. `src/utils/money.ts` parses to integer **paise** and formats as INR. Amounts, unit prices, EMI components and line items use names such as `amount_paise`; record payload validation and server constraints assume a 100-unit scale. Several form labels explicitly contain `₹`.
4. Dashboard totals, `fuel_history_page`, `fuelIntervals`, record lists, reports and CSV/JSON/PDF exports currently assume a single currency. Changing only the formatter or symbol would mislabel old data and could add unlike currencies. `src/features/progress` also has report-only currency fields whose units and provenance need separate review.
5. Roles, memberships, dates and time zones are per vehicle. Any currency design must preserve per-vehicle authorization, Pilot date restrictions, auditing and idempotent writes.

## Intended user experience

### Account setup and settings

- After verified Google or OTP sign-in, show a first-time profile screen with display name, the authenticated email as read-only, a searchable country selector, a searchable time-zone selector and a searchable currency selector. Do not claim an unverified email is verified.
- When a country is selected, suggest its commonly used currency and relevant time zones using versioned, reputable territory data. India → INR and `Asia/Kolkata`; United States → USD, with an explicit zone choice because a country may span multiple time zones. If the country has multiple currencies or no unambiguous current mapping, ask the user to choose; do not guess.
- Country, time zone and currency remain separately editable before saving. Explain when a country change proposes new defaults, and never overwrite a deliberate choice without confirmation. If a device locale supplies a suggestion, show it as a suggestion only; allow a manual search and selection.
- Allow later account preference edits. Explain that they affect defaults for **new vehicles**, not existing vehicles, historic amounts or other members. Existing accounts should keep their current time zone and INR assumptions until they deliberately choose otherwise; do not force a destructive profile reset.
- Track completion explicitly for newly created accounts rather than relying solely on a non-empty display name. Backfill the completion state for existing accounts so an upgrade does not unexpectedly block them; test Google/OTP, interrupted setup, retries and direct links.

### Vehicle setup and editing

- In Add Vehicle, preselect the saved account time zone and currency; allow the owner to override either. Explain which values are defaults and show them on review. Country may be inherited as useful context, but must not replace the actual selected IANA time zone.
- In Edit Vehicle, show its default currency and time zone. Only an authorized Owner may change them. If currency changes, clearly state: **past records retain their currencies; new records use the new default; no exchange-rate conversion occurs**. Audit the change. Preserve existing vehicle data, meter mode, fuel settings and timestamps.
- For shared vehicles, the **vehicle's default**, not a Pilot's private account preference, determines the initial currency for a new transaction. Show the code and symbol at entry time so all members understand the currency being recorded. Server-side authorization remains authoritative.
- For a newly recorded transaction, offer an explicit per-entry currency override if cross-border or mixed-currency purchases need to be supported; the selected transaction currency is stored with the transaction. If per-entry overrides are deferred, state the limitation clearly and still capture the vehicle default on every record. Never silently use the author's account preference in a shared vehicle.
- When editing a record, retain its original currency by default. If correcting an incorrectly recorded currency is supported, make it a separately authorized, audited correction with explicit confirmation and no automatic conversion. Otherwise require an owner to use the existing correction workflow and state the restriction.

### Country, time-zone and currency input UI

- Treat the input changes as part of the same future implementation as the database and money changes. Review the existing shared `src/features/garage/TimezoneField.tsx` and `timezone.ts` before extending or moving them; the account profile and vehicle form currently reuse this control. Do not add a second inconsistent time-zone picker or replace the working selector with free text.
- Use accessible, searchable and scrollable selectors for country, time zone and currency. Show the current value in the closed field and a clear selected state in the list; support keyboard, screen-reader labels, Android Back, cancel, large text, narrow screens and a visible no-results state. Keep long lists responsive, using virtualization or bounded pagination rather than rendering every option at once; users must still be able to reach every supported option.
- On account setup, select a country first, then suggest its currency and time zone. For a country with multiple zones, present a searchable list of its zones and require an explicit selection when no reliable unambiguous default exists. Allow searching all supported zones and currencies even when they are outside the chosen country. A zone must display its place and current UTC offset, with a short note that offsets may change; store its IANA identifier, not the displayed offset. A currency must display its ISO code, name and symbol where available.
- On Add Vehicle, show the inherited account currency and time zone clearly in the form, with editable selectors and the final chosen values on the review screen. Make the inherited-versus-overridden state understandable; do not require the user to reselect a valid inherited value. On Edit Vehicle, populate the saved vehicle values instead of resetting them from the account. Keep existing values and unsaved form state when a picker is opened and cancelled.
- Changing country must not silently overwrite a manually selected time zone or currency. When a change would replace either selection, present the proposed defaults and ask which to keep; cancelling retains the existing selections. Explain that account-default changes affect new vehicles and vehicle-default changes affect future entries, not historical records. Avoid claiming that a specific zone or currency is automatically correct for every user in a country.
- Provide explicit field-level validation and a recoverable error if the selected country, currency or zone is unavailable to the client or server. Preserve and display existing valid saved zone aliases even if a newer catalog uses a different canonical ID. Make the relationship between the device-supported zone catalog and server-supported PostgreSQL zone names explicit and test any discrepancies.
- Update monetary input controls along with these selectors: show an unambiguous currency code and relevant symbol in fuel, expense, EMI, line-item and filter fields; use the selected currency's actual fractional precision and appropriate keyboard; retain exact entered values and provide clear validation. A currency default change must not silently change the meaning of text already entered in a form. Show the original currency when editing a saved record.
- Plan loading, empty and retry states for profile/default retrieval and reference data. Keep the offline behavior consistent with the documented online-only policy; never invent a successful save or silently change a preference on a network error.
- Verify the selectors on both account and vehicle create/edit screens, including account inheritance, changing and cancelling overrides, multi-zone countries, DST, long labels, aliases, empty searches, large text and keyboard navigation. Test monetary inputs with zero-, two- and three-decimal currencies and a restored or edited record whose currency differs from the current default.

## Country and currency reference data

- Use an app-bundled, versioned country/territory catalog with ISO 3166-1 alpha-2 codes, localized display names and current currency/time-zone suggestions, sourced from Unicode CLDR and IANA time-zone data or another maintained, license-compatible authoritative distribution. Record version, source, license and a reproducible refresh procedure. Do not hand-maintain a small list and call it worldwide coverage.
- Store ISO 4217 currency codes (for example `INR`, `USD`, `JPY`, `KWD`), not a symbol: symbols such as `$` are ambiguous. Show code and currency name alongside the symbol where needed. Use IANA time-zone IDs, not a fixed offset or ambiguous abbreviation, and compute offsets for the relevant date. Local rules and daylight saving can change. [IANA time-zone database](https://www.iana.org/time-zones)
- Country does not always determine a single currency or time zone. Define a safe explicit-selection path for territories with ambiguous/missing data, discontinued currencies, or unsupported locale data. Do not silently fall back to INR for a user's explicit non-India selection.
- Support the full set of currencies only after validating currency-specific precision and the platform's formatter/data support. ISO/CLDR precision varies: currencies can use zero, two or three minor-unit digits. [Unicode CLDR currency fraction rules](https://unicode.org/reports/tr35/tr35-numbers.html)
- `Intl.NumberFormat` and locale data format values; they do **not** perform exchange-rate conversion. Keep display formatting separate from stored currency and value. [Unicode CLDR](https://unicode.org/reports/tr35/tr35-general.html)

Test a sample without user credentials using the documented public demo key if appropriate; the user's key was not used for this assessment. Independently verify whether the API provides named IANA zone identifiers or only offsets before relying on it for timezone selection; fixed offsets alone are insufficient.
- Prefer a validated, versioned and refreshable **bundled** minimal catalog for selectors, if the selected source's terms permit it. Avoid requiring a network call for each search; verify provenance and reconcile country codes, currency codes, zone aliases and daylight-saving rules with authoritative CLDR/IANA references. Preserve manual user overrides and previously saved valid IANA aliases. Do not assume either source is authoritative or complete without tests.
- A live API key was shared in the conversation. Treat it as exposed: revoke it in the provider's API Keys page and replace it before any future use. Never copy it into this document, Git history, app source, mobile bundle, `EXPO_PUBLIC_*` values, screenshots, logs or URLs. If a future runtime integration needs a private key, keep it in managed server-side secrets behind a narrowly scoped server function and use error handling and caching; a server proxy is not required if a licensed build-time catalog meets the need. - Before selecting a provider, compare actual sample records and terms: India (`IN`, `INR`, `Asia/Kolkata`), Canada (`CA`, `CAD`, multiple IANA zones), a multi-currency/territory case and current JPY/KWD fraction digits. Deduplicate zones; check territory membership and aliases against IANA/CLDR rather than assuming a shared UTC offset means the same time zone. Record the source version, retrieval date, licensing and reconciliation tests.

## Data model and financial integrity

Design and review additive migrations and versioned APIs before implementation. Do not modify previously applied migrations, delete existing data, or run a destructive reset against a real environment.

1. Add profile country code, preferred ISO currency and onboarding-completion/version fields with validated server-side constraints. Preserve the existing profile time zone. Decide whether country/time-zone/currency are mandatory at setup; make their defaults and migrated status explicit.
2. Add a vehicle default currency (and country if actually needed), with server-side validation, owner-only mutation, audit event and concurrent-update protection. New vehicles inherit the owner's saved defaults; existing vehicles receive an explicit INR legacy default without rewriting history or changing their stored time zones. Extend typed schemas, `list_my_vehicles`, `save_vehicle`, development mode and tests. Any RPC signature or return-shape change must account for dependent functions and granted permissions.
3. Add an immutable transaction currency code and an integer minor-unit amount for each fuel and expense record, plus associated price, EMI and line-item amounts. Consider storing a currency/precision snapshot or an equivalent versioned representation so historical records remain interpretable even if reference data changes. The record currency is independent of the account and the vehicle's current default once saved.
4. Backfill legacy fuel and expense records as INR using the current authoritative paise meaning: **100 paise = INR 1**. Backfill all associated monetary fields and line items consistently. Confirm the source data before applying the migration. Preserve original payloads, revisions, timestamps, audit events and receipts; define reconciliation queries and rollback/recovery before deploying.
5. Replace or version misleading `_paise` APIs and payload keys without losing data. During transition, maintain a clearly specified compatibility representation where necessary; ensure no dual-write divergence, overflow, rounding mismatch or accidental reinterpretation. Currency changes and record writes must be transactionally validated server-side under the existing per-vehicle permissions.
6. Use exact integer/decimal arithmetic and currency-specific fraction digits for amounts; validate numeric range and avoid JavaScript floating-point money calculations. Test zero- and three-decimal currencies as well as two-decimal INR/USD. Decide separately how unit prices retain sufficient precision for fuel quantities and how two-of-three calculations round and validate; do not silently round a price into an inconsistent receipt.
7. Review non-ledger monetary values: EMI/principal/interest, expense line items, maintenance-linked reminders, custom Daily Progress currency answers, reports, defaults and exported data. A custom field without recorded currency provenance must not be silently relabeled; define a legacy representation and presentation before migration.
8. Restrict financial reads and mutations with SQL/RPC/RLS, not client-side buttons. Cross-vehicle access, Pilot restrictions, revocation, audit trails and operation-id retry guarantees remain mandatory. Never place privileged keys in the client.

## Screens, calculations and exports

- Replace hard-coded `₹`, INR and `/ 100` assumptions in inputs, validation, errors, record cards and money helpers. Accept and display the allowed fractional digits for each selected currency, show unambiguous ISO codes, and validate server-side too.
- Keep amounts in their recorded currency when listing or editing. Home, Fuel and Expense summaries, date/amount filters, analytics and reports must **group totals by currency** or require a clearly selected currency. Never add INR and USD into a single total or compare amounts of different currencies as if they had the same value. Update the paginated fuel RPC and response contract as well as local-development paths.
- Full-to-full efficiency may use quantities and meter readings when otherwise valid, but cost totals and cost per distance must be separated by currency; do not combine incompatible currency intervals. Respect fuel-type/unit and timezone rules already in place.
- CSV, JSON and PDF must explicitly carry currency codes and exact amounts/minor-unit scale, including line items and any summaries; version export schemas if necessary. Maintain CSV formula-injection protection and existing authorization checks. Test old exports and imported consumers before changing column meaning.
- If currency conversion is wanted in a future feature, it requires a separately approved exchange-rate source, rate time, conversion basis, rounding and clear original/converted labels. This plan does not enable conversion.

## Compatibility and rollout gate

1. Inventory every current app version, database/RPC path, RLS policy, export consumer and deployed migration. Verify the exact linked project and take a restorable, tested backup before production changes.
2. Implement schema and versioned APIs additively in a disposable environment; verify backfill and RLS using realistic old and new data, including totals and exports. Test that currency is not writable across vehicles or silently changed on edit.
3. Plan a **fail-closed compatibility gate** before any non-INR record is enabled. Old clients hard-code INR and may call existing table/RPC paths, so a UI-only version prompt or an untrusted client-supplied version header is insufficient. Design and prove server-side restrictions/versioned authorized paths so old clients cannot read non-INR values as INR, write ambiguous amounts, or display incomplete mixed-currency totals as complete. If that cannot be guaranteed, block non-INR writes until incompatible clients are retired or access is safely migrated. Do not deploy a backend change that causes old clients to mislabel data.
4. Deploy reviewed migrations and new app code in a coordinated, reversible sequence. Verify migration history, backfill counts, authorized server reads/writes and current client behavior. Enable non-INR entries only after the compatibility and security gates pass. Never reset production or mark failed migrations as applied manually.
5. Document verification, backup and rollback/forward-repair procedures, user-facing changes, external operator steps and actual PASS/FAIL/BLOCKED results in the relevant stage handoff.

## Acceptance and testing

- New verified account selects India → IST/INR; US → USD and an explicit applicable time zone; manual overrides persist after sign-out/sign-in. Google and OTP paths, interrupted onboarding and existing accounts work without unexpected lockout.
- New vehicles inherit preferences; owner overrides persist. Existing vehicles and old INR entries remain INR after account or vehicle defaults change. No financial data is rewritten as a different currency.
- At least one shared vehicle has Owner and Pilot accounts with different personal currency settings: new entry follows the vehicle default, authorized overrides behave as specified, and revoked/unauthorized users cannot view or write financial records.
- Mixed INR/USD data produces separate labeled totals and correct per-currency filters in Home, Fuel, Expenses, analytics, reports and exports. Existing full-to-full interval rules remain correct. Currency corrections, concurrent changes and idempotent retries are tested.
- Validate INR/USD, JPY and KWD or equivalent 2/0/3-decimal currencies; check exact arithmetic, fractional limits, huge values, unit-price rounding and invalid codes. Verify timezone offsets across DST and a country with multiple zones; preserve named-zone semantics.
- Run unit and integration tests, chronological migrations and RLS tests on local Supabase, old/new client compatibility tests, typecheck/lint/format, Expo config and Android build, plus real device and real verified-account flows. Record skipped or blocked checks accurately.

## Open implementation decisions

- Whether per-entry currency override is required at first release or vehicle default alone is sufficient; both require a currency snapshot per transaction and mixed-currency handling after a default changes.
- Username rules and whether it is optional, unique, public to vehicle members or merely a second private profile field.
- Catalog provider/version and update mechanism; the exact supported set must reflect currencies the client, database, input precision and reports can actually handle.
- The server-enforced legacy-client compatibility mechanism and deployment cutoff. This must be resolved and tested before non-INR transactions are enabled.
